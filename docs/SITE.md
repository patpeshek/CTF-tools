# Сайт: архитектура и песочница

Дизайн-документ. Решает тикеты #141 (архитектура) и #142 (песочница).
Код здесь не предлагается — только как устроено и почему. Правки обсуждаемы:
открытые вопросы собраны в конце.

## 1. Что строим и границы

Сайт — это оболочка над движком `solve`, а не новый движок. Пользователь
(команда на турнире) кидает файл, текст условия, URL или `host:port`, сайт
запускает `solve --json` в изоляции и показывает живой ход решения и флаг.

**В объёме:** приём задания, запуск движка в песочнице, стрим хода решения,
страница результата, закрытый доступ команды, офлайн-режим на ноутбуке.

**Вне объёма (отдельные тикеты):** каталог инструментов (#153), история и
заметки (#154), живые сервисы/PPC через сайт (#155). Они встают поверх этой
основы и её не меняют.

**Главное ограничение, определяющее всё остальное:** загружаемый файл —
**враждебный**, а движок к этому не готов. На доске открыты #50 (RCE в
`git_hunt` через чужой `.git`), #19 (плагины исполняются при запуске), #13
(бомбы архивов), #43 (чтение секретов из соседних папок). Значит движок
нельзя считать доверенным и нельзя запускать на хосте. Отсюда — песочница в
центре архитектуры, а не сбоку.

## 2. Модель угроз

Что может прислать атакующий (или недоверенный автор задачи) под видом
задания:

| Вектор | Пример | Чем опасно |
|---|---|---|
| RCE через данные | `.git` с `textconv`, имя файла `a&calc&.bin` для Ghidra | выполнение кода при разборе |
| Исполнение движком | esolang-интерпретатор, плагин в `plugins/` | код в контуре движка |
| Бомбы | zip-бомба, PNG с гигантским zTXt, вложенные архивы | память и диск хоста |
| Выход за песочницу | zip-slip, traversal, символические ссылки | запись за пределы задания |
| Утечка | движок читает соседние файлы/секреты, затем «решает» на сервере | эксфильтрация |
| Сеть | задание инициирует исходящие соединения | сервер как плацдарм |
| Исчерпание ресурсов | бесконечный цикл, форк-бомба | отказ в обслуживании |

**Вывод:** движок внутри песочницы считаем уже скомпрометированным. Задача
песочницы — чтобы его компрометация ничего не давала: нет сети, нет хоста, нет
прав, нет соседних заданий, жёсткие лимиты, эфемерность.

## 3. Компоненты

```
Браузер (статичный UI)
   │  HTTP: загрузка; SSE: поток событий
   ▼
Бэкенд-оркестратор  (единственный сетевой/привилегированный компонент)
   │  приём → валидация размера/типа → постановка в очередь
   │  запуск контейнера на задание → relay JSON-событий → уборка
   ▼
Песочница на задание  (эфемерный контейнер, по одному на задание)
   │  solve --json -   (без сети, root только для чтения, лимиты, не-root)
   ▼
Эфемерное хранилище артефактов  (скретч задания, удаляется после выдачи)
```

Принцип: **оркестратор никогда сам не разбирает присланный файл.** Он только
валидирует метаданные (размер, заявленный тип), кладёт файл в скретч задания и
запускает песочницу. Весь разбор — внутри контейнера.

## 4. Контракт движка (готов, #82)

`solve` уже отдаёт машинный поток: `--events -` пишет живой поток JSON-строк
в stdout по мере работы (всё человеческое уходит в stderr); `--json` добавляет
в конце итоговую сводку одним объектом. Для живого хода решения на сайте нужен
именно `--events -`. Это и есть API, на который садится бэкенд — ничего
дополнительно изобретать не нужно.

Каждая строка — объект `{"event": <тип>, "t": <секунды от старта>, ...поля}`,
flush после каждой. Типы событий:

| event | Поля | Когда |
|---|---|---|
| `plan` | `target`, `mode`, `kind`, `statement`, `steps[]` | определён тип, построен план |
| `step_start` | `n`, `tool`, `args[]`, `why`, `timeout` | шаг начат |
| `step_end` | `n`, `tool`, `args[]`, `why`, `timeout`, `status`, `reason`, `rc`, `seconds`, `output_tail`, `flags[]`, `leads[]`, `stubs[]` | шаг закончен |
| `flag` | `n`, `tool`, `flag`, `flags[]` | найден настоящий флаг |
| `lead` | `n`, `tool`, `text` | зацепка (не флаг) |
| `done` | `status`, `flag`, `steps`, `elapsed` | прогон завершён |

`status` шага: `ok` / `fail` / `timeout` / `killed` (другой шаг нашёл флаг) /
`skipped`. Поток закрывается событием `done`; при `--json` в конце ещё и полный
объект результата одной строкой.

**Соответствие экранам из макета:** `plan.steps` → список шагов; `step_start`
/`step_end` → лента хода; `flag` → проявление флага; `lead` → блок «зацепки»
в сценарии «флаг не найден». То есть фронтенд из макета ложится на этот поток
один-в-один.

Фронтенд получает поток через SSE (Server-Sent Events): бэкенд читает stdout
контейнера построчно и пересылает как есть. SSE, а не WebSocket — поток
односторонний (сервер → браузер), переподключение из коробки, проще.

## 5. Спецификация песочницы (#142)

Один контейнер на задание, эфемерный (`--rm`). Базовый профиль запуска:

- `--network none` — сети нет. Веб-задания (recon/param по URL) — отдельный
  режим с явным egress-allowlist только на хост цели (см. §7).
- `--read-only` корневая ФС; запись только в скретч: `--tmpfs
  /work:rw,size=512m,nosuid,nodev,noexec`.
- Вход монтируется только на чтение: `-v <job>/in:/in:ro`.
- Память: `--memory 1g --memory-swap 1g` (OOM-kill вместо качелей swap).
- CPU: `--cpus 2`. Процессы: `--pids-limit 256` (против форк-бомб).
- Файлы: `--ulimit nofile=1024`, `--ulimit fsize=<cap>` (против бомб на диск).
- Права: `-u 10000:10000` (не-root), `--cap-drop ALL`,
  `--security-opt no-new-privileges`, seccomp по умолчанию.
- Никакого проброса docker.sock, никаких host-mount, кроме скретча задания.
- Настенный таймер — у оркестратора: снять контейнер (`docker kill`) через N
  секунд независимо от того, что внутри. Движок `--time` этому не замена.

**Усиление, если доступно:** рантайм gVisor (`runsc`) как второй слой изоляции
системных вызовов; на ноутбуке — rootless Podman, чтобы сам демон не требовал
root. Образ — минимальный (slim-Python + только нужные бинари: hashcat/Ghidra
подключаются как отдельные опции, не в базовом образе).

**Почему контейнер, а не просто лимиты процесса:** движок исполняет чужой код
(esolang, Ghidra, git textconv). Ограничений `resource`/таймаутов на хосте
недостаточно — нужна изоляция ФС, сети и прав, которую даёт только контейнер
(или ВМ). Это тот случай, где «на авось» нельзя.

## 6. API бэкенда (эскиз, тикет #143)

- `POST /jobs` — multipart: файл и/или текст условия, формат флага, режим
  (offline/web). Валидация размера и типа. Ответ: `{job_id}`. Файл кладётся в
  скретч задания, задание — в очередь.
- `GET /jobs/{id}/events` — SSE-поток событий движка (см. §4) по мере работы.
- `GET /jobs/{id}` — итог: статус, флаг, план, артефакты.
- `GET /jobs/{id}/artifacts/{name}` — отдать артефакт (вырезанный файл и т.п.),
  только из скретча задания, имя валидируется.
- `DELETE /jobs/{id}` — снять и удалить.

Очередь и воркеры (#144): начать с простого — таблица заданий в памяти и пул
воркеров-оркестраторов; Redis/RQ добавлять, только когда упрёмся в
параллельность. Хранилище (#145): скретч на задание + срок хранения, уборка по
таймеру.

## 7. Режимы и сеть

- **Offline (турнир, по умолчанию).** Сети у контейнера нет вообще. Всё
  крипто/стего/форензика/реверс/PPC работает. Это основной режим.
- **Web-задание (опционально).** Для recon/param по URL нужен выход наружу.
  Тогда контейнер поднимается с egress-allowlist **только на хост цели**
  (iptables/прокси на уровне оркестратора), остальное закрыто. Это явный выбор
  пользователя на форме, не поведение по умолчанию.

Защита самого сайта (#152) — отдельный тикет: SSRF через URL-цель, traversal в
выдаче артефактов, XSS в выводе инструментов (вывод движка — не доверенный
текст, экранировать при показе).

## 8. Офлайн-развёртывание (тикет #151)

Финалы проходят на ноутбуке с Kali без интернета. Значит:

- всё поднимается одной командой через `docker compose` (бэкенд + статика);
- образы движка и базовый образ песочницы собраны и сохранены заранее
  (`docker save`/`load`), ничего не тянется из сети при старте;
- словари и внешние утилиты кладутся в образ песочницы на этапе сборки.

Это даёт ровно ту переносимость, ради которой обычно смотрят на «один
бинарник»: снимок окружения, работающий без сети.

## 9. Порядок работ (зависимости тикетов)

```
#141 архитектура (этот документ)
   └─ #142 песочница ──┬─ #143 API загрузки/запуска
                       ├─ #147 ход решения (SSE)  ← контракт готов (#82)
                       └─ #145 хранилище/уборка
#146 форма ввода ─ #148 страница результата ─ #149 вход команды
#151 офлайн-сборка ─ #152 защита сайта ─ #156 сквозные тесты
```

Критический путь — **песочница**. Без неё нельзя безопасно запустить ни одно
задание, поэтому она первая после этого документа. Полный UI держим до
починки P0 ядра (find_flags режет `picoCTF`, sniff не знает TAR): сайт обязан
отдавать правильный флаг, иначе красивый интерфейс выдаёт мусор.

## 10. Открытые вопросы (решить вдвоём)

2. **Стек бэкенда:** FastAPI (тот же Python, что движок, минимум склейки) —

3. **Ghidra/hashcat в песочнице:** тяжёлые и опасные; включать опцией в более

4. **Параллельность:** сколько заданий одновременно на турнире реально нужно?
   От этого — очередь в памяти или полноценная (#144).
5. **Хранение:** артефакты только на время сессии или история прогонов (#154)?
