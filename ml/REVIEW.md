## 1. Реверс-модель: классы бинарников

**Что.** `ml/rev_features.py` (+ `ml/rev_data.py`, `ml/relabel.py`) — модель
отвечает не «это elf», а «что за бинарник»: `elf_go`, `elf_rust`,
`elf_packed`, `elf_dynamic`, `elf_static`, `elf_stripped`, `elf_shared`,
`pe_native`, `pe_dotnet`, `pe_packed`.

**Логика.** Метки детерминированные, из самого файла: маркеры Go/Rust/UPX/.NET,
`.interp`, `.symtab`, ET_DYN без PT_INTERP → `elf_shared` (иначе 1900 из 2337
файлов схлопывались в `stripped`).

**Данные.** 2337 уникальных ELF/PE из `sajjadium/ctf-archives` (SHA-256 дедуп,
первые 4 МБ, 8 потоков, ~5 минут).

**Метрики.** test 85.5%, top-2 92.6%. Слабо: `elf_go` 0/2, `elf_rust` 2/4.

**Смотреть:** корректность `label_of`, границы классов, нет ли утечки
метки в признаки.

## 2. Pwn-модель: профиль защит

**Что.** `ml/pwn_features.py` — NX/PIE/canary/RELRO/static из ELF-заголовков;
классы `pwn_ret2win`, `pwn_ret2libc`, `pwn_canary_nopie`, `pwn_canary_pie`,
`pwn_static`, `pwn_shellcode`, `pwn_pe`.

**Логика.** RELRO считается по биту `DF_BIND_NOW`/`DF_1_NOW` в `.dynamic`, а
не по подстроке «BIND_NOW» (у `pwn/checksec.py` там баг — 10 ложных `partial`).
NX для ET_REL (.ko) = None, а не True.

**Метрики.** test 86.0%, top-2 93.2%. Слабо: `ret2libc` 4/22, `canary_nopie` 3/8.

**Смотреть:** согласованность `profile()` и `label_of()`; не меняет ли правка
NX для .ko метки (не должна).

## 3. Обучение: мягкие веса классов

**Что.** `ml/train.py --class-weights` — вес `sqrt(N/(K*n))`, clip 0.5..4.

**Почему так.** Жёсткие веса (обратная частота) уронили общий acc до 0.114;
мягкие подняли редкие классы (`elf_static` 0→67%, `ret2libc` 0→18%) почти
без потерь (85.5% против 86.6%).

**Смотреть:** формула весов, отсутствие утечки весов в валидацию.

## 4. Интеграция в солвер

**Что.** `solve.py`:
- `REV_TOOLS` — класс → первые инструменты;
- `smart_order(..., hint=...)` — вклад реверс- и pwn-моделей поверх роутера
  (роутер не отключён);
- `_task_hint`/`_binary_candidates` — модель включается по смыслу задачи
  (условие `reverse`/`pwn`, расширения, бинарник в папке), обход папки ≤4000 файлов;
- шаги `lang`, `checksec`, `symbols`, `autopwn`, `libcoff` для ELF/PE;
- probe-фаза в `run_many`: первые 2 шага последовательно, **только когда
  загружен роутер** (иначе ломается `solve.py admin config`);
- `statement_steps` → `autopwn --remote host:port`, если в условии есть адрес.

**Замер.** Правильный первый инструмент класса: top-5 13% → 88%, медиана 6 → 4.
Шагов на 3 задачах: 22 против 29 без моделей.

**Смотреть:** не ломает ли `hint` не-ELF сценарии; порядок шагов; что
`--rules-only` ведёт себя как раньше.

## 5. Autopwn: статический payload

**Что.** `pwn/autopwn.py`: профиль защит → цель (`win` или `system`+`/bin/sh`
+ `pop rdi;ret`) → смещение из capstone (`lea rdi,[rbp-X]`, `sub rsp,N`) →
payload hex + сниппет pwntools. `--run` проверяет запуском в WSL,
`--remote host:port` отправляет на сервис.

**Проверено.** Собранная задача (`gets(buf[64])` + `win`): `win @ 0x401156`,
offset 72, payload напечатал `CTF{autopwn_works}`. Солвер решил её сам за ~4 с.
Через `socat`-сервис флаг получен на шаге 4.

**Риски.** Запуск чужих бинарников в WSL без песочницы, включён по умолчанию
(`SOLVER_RUN=0` отключает) — решение пользователя, но ревью нужно.

**Смотреть:** эвристика смещений (28 из 40 бинарников с `main`), отказы при
канарейке/PIE, таймауты сокета и subprocess.

## 6. Сайт: поля pwn и валидация

**Что.** `site/static/index.html`: host/IP, порт, способ (nc/socat/ssh/http),
пароль. Уходят в условие как `[адрес]`, `[подключение]`, `[пароль]` + строка
`сервис: host:port`.

**Валидация.** Клиент: адрес без порта/способа — не запускать; порт/способ без
адреса — ошибка. Сервер: адрес без `:` → HTTP 400.

**Проверено.** 400 без порта, 200 с портом; `parse_statement` видит
`hosts: ['10.0.0.5:31337']`, `category: pwn`.

**Смотреть:** не сломана ли отправка формы без pwn-полей; XSS/инъекции в
значениях (они идут в текст условия).
